# ISO 26262:2018 software: code review checklist

Source: ISO 26262:2018, Road vehicles, Functional safety (second edition, December 2018), https://www.iso.org/standard/68383.html. This checklist covers the software side: Part 6, Product development at the software level (https://www.iso.org/standard/68388.html), and parts of Part 8, Supporting processes (https://www.iso.org/standard/68390.html). The checks below are written in our own words. The IDs are written as `<part>-<clause>`, so `6-8.4` means Part 6, clause 8.4 (requirements and recommendations for software unit design and implementation). Clause 5.4.2 and 5.4.3 of Part 6 are cited at that level. Other IDs are cited at clause level, because the sub-requirement numbers aren't freely published.

Part 6 clauses used: 5 general topics, 6 software safety requirements, 7 software architectural design, 8 software unit design and implementation, 9 software unit verification, 10 software integration and verification, 11 testing of the embedded software. Part 8 clauses used: 7 configuration management, 8 change management, 11 confidence in the use of software tools, 12 qualification of software components.

Much of ISO 26262 is about process, hazard analysis and safety cases. Code review can only see how the software itself is written, structured and tested. The checks below are the ones that show up in code, build settings and test files. They depend on the safety level (ASIL) of the software, so judge each check against the level the project states.

## When this applies

Apply these checks to changes in software that belongs to, or can affect, a safety-related function in a road vehicle: application code, drivers, configuration, build and compiler settings, test code, and tool or CI setup. If the project states no safety level, or the change touches none of these areas (for example documentation or styling), report this standard as `not_applicable`.

## Checks

### [ISO 26262 6-5.4.2] The language, coding rules and tools suit safety-related software
Look for: a change that moves to a language, subset or compiler setting the project's safety plan doesn't allow, such as dynamic memory, exceptions or language features the coding rules ban. Coding-rule checks (MISRA-style or the project's own) removed from the build or set to warnings only.
Decided from code: partly. The project's chosen rules and safety level are set outside the repository.

### [ISO 26262 6-5.4.3] Language use is limited where the language is unsafe
Look for: new use of constructs the project limits, such as unchecked casts, unrestricted pointers, implicit conversions, `goto`, or unsafe blocks, with no recorded reason. Rule suppressions without a justification comment.
Decided from code: yes, where the project states its rules.

### [ISO 26262 6-6] Software safety requirements can be traced to code
Look for: safety-related behaviour changed with no reference to the requirement it serves, in a project that links code, tests and requirements by ID. Requirement IDs in comments or tests that no longer exist. Safety requirements removed from the repository without matching code changes.
Decided from code: partly. The requirements often live in a separate tool.

### [ISO 26262 6-7.4] Architecture keeps safety-related parts separate, with run-time error detection and safe states
Look for: lower-rated or unrated components writing to the memory, state or outputs of safety-related components. Shared globals across partitions. Removed memory-protection or partition settings (MPU/MMU, OS task priorities). Removed or weakened range and plausibility checks, watchdog servicing, timeouts, program-flow monitoring, CRCs on safety data and redundant computation. Error handling that logs and continues instead of moving to the defined safe or degraded state, and empty default branches in code that drives actuators.
Decided from code: partly. The intended partitions and the safe state come from the architecture and safety concept.

### [ISO 26262 6-8.4] Units are simple, well-defined, initialised and bounded
Look for: very long or deeply nested functions, many exit points, many parameters, shared mutable globals, recursion and hidden state. Variables used before initialisation, implicit conversions that lose data, unchecked values from sensors or other components, unbounded loops, floating-point equality, and unnamed magic numbers for safety limits. Dynamic allocation after start-up, unbounded queues, and blocking calls in time-critical tasks. Complexity limits removed from checks.
Decided from code: partly. Real timing and stack needs are known only from measurement.

### [ISO 26262 6-9] Units are verified, and the tests and static analysis cover the changed behaviour
Look for: changed safety-related functions with no new or updated unit tests, including error and boundary cases. Tests deleted, skipped or loosened. Coverage gates lowered. Static analysis or coding-rule checks removed, set to continue on failure, or narrowed by new suppressions. Compiler warnings no longer treated as errors in safety-related modules.
Decided from code: yes.

### [ISO 26262 6-10] Integration tests exercise the interfaces between components
Look for: interfaces between safety-related components changed with no integration tests. Fault-injection or error-handling tests removed. Mocks that hide the error responses the real component gives.
Decided from code: yes.

### [ISO 26262 6-11] Tests run on the target, or the gap to the target is handled
Look for: tests that run only on a host machine for code that depends on the target hardware, timing, or compiler. Test builds that use different compiler options from the release build, with no stated reason.
Decided from code: partly. Test hardware setups are usually outside the repository.

### [ISO 26262 8-7] Every safety-related item is under configuration control
Look for: binaries, generated code, calibration data, or libraries committed with no version or source. Build inputs fetched at build time from moving references. Build settings that change per developer machine. Missing version identifiers in release builds.
Decided from code: yes.

### [ISO 26262 8-8] Changes to safety-related software go through change management
Look for: changes to safety-related code that bypass the project's review rules, such as removed required reviewers, or direct edits to generated or released code. Large unrelated changes bundled with a safety fix.
Decided from code: partly. The change records and impact analysis are usually kept in other tools.

### [ISO 26262 8-11] Software tools that can add or hide faults are controlled
Look for: compiler, linker, code generator, static analyser or test tool versions that change, or are unpinned, in the build files. Tool options that change the generated code, such as optimisation levels or removal of checks. Tool outputs used as evidence with no pinned version.
Decided from code: partly. The tool confidence level and qualification evidence are kept outside the repository.

### [ISO 26262 8-12] Reused and third-party software components are identified and checked
Look for: new or updated third-party libraries, operating systems or middleware in safety-related builds with no version pin, license note, or record of how it was evaluated. Vendored code changed locally without a record.
Decided from code: partly. Qualification evidence is usually outside the repository.
