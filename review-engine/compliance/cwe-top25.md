# CWE Top 25 (2025): code review checklist

Source: MITRE, 2025 CWE Top 25 Most Dangerous Software Weaknesses, https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html. The checks below are written in our own words. The IDs are the CWE weakness IDs, so a finding can be traced back to the CWE entry. This checklist follows the 2025 list. Weaknesses that were in earlier lists but are not in the 2025 list are not used.

The list ranks the weaknesses most often behind real, published vulnerabilities. It is about code-level mistakes, so most of its entries can be seen directly in a change.

## When this applies

Apply these checks to changes in application and library code, including web handlers, API endpoints, parsers, file handling, native code and database access. The memory-safety checks (CWE-787, CWE-125, CWE-416, CWE-476) matter only for languages without automatic memory safety, such as C, C++ and unsafe blocks in Rust or Go.

If the change touches none of this, such as documentation, styling or copy, report this standard as `not_applicable`.

## Checks

### [CWE-79] User input is encoded before it is shown in a page
Look for: user-controlled values written into HTML, attributes, scripts or URLs without encoding for that place. `innerHTML`, `document.write`, `dangerouslySetInnerHTML`, `v-html`, template filters like `|safe` or `{!! !!}`, and server templates with auto-escaping turned off, fed from request data, stored data or URLs.
Not a breach: content that goes through a trusted sanitiser with a strict allow-list, or fixed strings.
Decided from code: yes.

### [CWE-89] Database queries don't build SQL from user input
Look for: SQL assembled by string concatenation, f-strings or template literals with request values, including `ORDER BY` columns and table names taken from input. Raw query helpers of an ORM called with joined strings.
Not a breach: parameterised queries, and identifiers chosen from a fixed allow-list.
Decided from code: yes.

### [CWE-352] State-changing requests can't be forged from another site
Look for: new POST, PUT, PATCH or DELETE handlers that use cookie-based sessions with no CSRF token, same-site cookie setting or origin check. CSRF protection switched off for a route or framework-wide. State changes made on GET requests.
Not a breach: handlers that only accept a bearer token sent in a header.
Decided from code: yes.

### [CWE-862] Every sensitive action checks that the caller is allowed to do it
Look for: new endpoints, jobs, GraphQL resolvers or admin functions that never check a permission, while sibling code does. Checks done only in the UI. Middleware that is missing from one route.
Decided from code: yes, for code in the repository. Permissions enforced by a gateway outside the repository are not visible.

### [CWE-863] The authorisation check itself is correct
Look for: checks that test the wrong thing, such as "is logged in" where "is the owner" is needed, role comparisons that are off, checks that fail open on errors, and conditions where a missing value counts as allowed. Permission cached across users or tenants.
Decided from code: yes.

### [CWE-787] Native code doesn't write outside the bounds of a buffer
Look for: writes into arrays or buffers with an index, length or offset that isn't checked against the size. Unsafe copy functions (`strcpy`, `sprintf`, `gets`, `memcpy` with an untrusted length), integer overflow in a size calculation before allocation, off-by-one in loops, and `unsafe` code that skips bounds checks.
Decided from code: yes.

### [CWE-125] Native code doesn't read outside the bounds of a buffer
Look for: reads with an unchecked index or length, string functions on data that may lack a terminator, a length field read from input and trusted, and loops that run past the end by one.
Decided from code: yes.

### [CWE-416] Memory isn't used after it has been freed
Look for: pointers or references used after `free`, `delete` or a move, containers modified while iterated, callbacks holding raw pointers to objects that can be destroyed, double free, and error paths that free memory twice or free it and keep using it.
Decided from code: partly. Some cases depend on object lifetime across many files.

### [CWE-22] File paths built from user input can't escape their folder
Look for: user-supplied file names or paths joined to a base folder with no normalising and no check that the result is still inside the base. `../` and absolute paths accepted, archive entries extracted by name (zip slip), and downloads or includes selected by a request parameter.
Not a breach: names chosen from a fixed list, or generated by the server.
Decided from code: yes.

### [CWE-78] Operating system commands don't include user input
Look for: `exec`, `system`, `popen`, `child_process.exec`, `os.system` or `subprocess` with `shell=True`, given strings built from request data, file names or settings. Arguments passed to shell tools without a `--` separator, so values can act as options.
Not a breach: an argument array with fixed program and validated arguments.
Decided from code: yes.

### [CWE-94] User input is never run as code
Look for: `eval`, `exec`, `Function()`, `vm.runInContext`, dynamic `import` or `require` of a user-chosen path, server-side template engines fed with user-written templates, expression-language evaluation of input, and plugin or script loading from user-writable locations.
Decided from code: yes.

### [CWE-434] Uploaded files are limited by type, size and where they are stored
Look for: uploads accepted with no check of type by content, extension allow-list or size limit. Uploads saved inside a folder that is served or executed, or with the client-supplied name. Executable types such as `.php`, `.jsp`, `.html` or `.svg` allowed where they will be served back.
Decided from code: yes.

### [CWE-476] Pointers and optional values are checked before use
Look for: results of functions that can return null (`malloc`, lookups, `find`, `getenv`, parsers) used with no check. Optional values force-unwrapped (`!`, `.unwrap()`, `.get()` on an empty optional) on data that can legitimately be missing.
Decided from code: yes.

### [CWE-502] Untrusted data isn't deserialised into objects
Look for: `pickle.loads`, `yaml.load` without a safe loader, Java `ObjectInputStream`, .NET `BinaryFormatter`, PHP `unserialize`, `node-serialize`, or a JSON setting that allows type names to choose the class, used on data from requests, files, queues or caches that others can write to.
Not a breach: data signed and checked before it is read, or formats that carry plain data only.
Decided from code: yes.

### [CWE-200] Sensitive information isn't exposed to people who shouldn't see it
Look for: responses that return whole database records including password hashes or internal fields, detailed stack traces and SQL errors sent to clients, secrets, tokens or personal data written to logs or URLs, debug endpoints left on, and verbose messages that show whether an account exists.
Decided from code: yes.

### [CWE-306] Critical functions require the caller to sign in
Look for: new administrative, payment, account-change, reset or internal endpoints with no authentication at all. Authentication middleware left off a route group. Debug, health or management endpoints that return data or change state and are open to the network.
Decided from code: yes, for code in the repository.

### [CWE-918] The server doesn't fetch addresses chosen by the user without limits
Look for: server-side requests (`fetch`, `requests.get`, `HttpClient`, webhook calls, image or URL previews, PDF renderers) to a URL taken from input with no allow-list of hosts. No block on private, loopback and link-local addresses such as cloud metadata endpoints, and redirects followed without re-checking.
Decided from code: yes.

### [CWE-639] Records requested by ID are checked against the caller
Look for: handlers that load a record by an ID from the request (path, query, body) and return or change it without checking that it belongs to the caller or their tenant. Sequential or guessable IDs combined with no ownership check.
Decided from code: yes.

### [CWE-770] Work and memory a caller can trigger have limits
Look for: no rate limit on expensive or sign-in endpoints, unbounded request bodies, page sizes, upload sizes or file counts, loops or allocations sized from input, queues and caches that grow without a cap, and missing timeouts on outgoing calls. Regular expressions with catastrophic backtracking on user input.
Decided from code: partly. Limits set in a gateway or proxy are not visible in the repository.

### [CWE-20] Input is checked for what the code expects before it is used
Look for: request fields, headers, file contents and message payloads used with no check of type, range, length, format or allowed values. Validation only in the client. Numbers from input used as sizes, indexes or counts without bounds.
Decided from code: yes.
