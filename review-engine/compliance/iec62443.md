# IEC 62443 (4-1 and 4-2): code review checklist

Source: IEC 62443-4-1:2018, Security for industrial automation and control systems, Part 4-1: Secure product development lifecycle requirements, https://webstore.iec.ch/en/publication/33615 (also published as ANSI/ISA-62443-4-1-2018), and IEC 62443-4-2:2019, Part 4-2: Technical security requirements for IACS components, https://webstore.iec.ch/en/publication/34421. The checks below are written in our own words. The IDs are the practice IDs of Part 4-1 (SM, SR, SD, SI, SVV, DM, SUM, SG) and the component requirement IDs of Part 4-2 (CR), so a finding can be traced back to the official text.

Part 4-1 describes the processes a product supplier follows to build and maintain secure products. Part 4-2 describes technical security requirements for the components of an industrial control system, such as embedded devices, network devices, host devices and software applications. Many requirements are process records. The checks below are the ones where evidence shows up in code, configuration, dependencies and pipelines.

## When this applies

Apply these checks to changes in software, firmware and configuration for industrial automation and control products and their supporting services: application and embedded code, communication interfaces, authentication, logging, update functions, dependencies, build and release pipelines. If the change touches none of these (for example documentation or styling), report this standard as `not_applicable`.

## Checks

### [IEC 62443 SM-6] Released files are protected against tampering
Look for: release pipelines that stop signing or hashing packages and firmware, or stop publishing checksums. Signing keys moved into the repository, or into plain pipeline variables. Artifacts built or uploaded by hand.
Decided from code: yes, for release pipelines in the repository.

### [IEC 62443 SM-7] The development and build environment is secured
Look for: CI actions or build images pulled by a moving tag instead of a fixed version or hash. Pipeline tokens with broad rights. Secrets exposed to builds of untrusted changes, or printed in logs. Tools downloaded in the pipeline with no hash or signature check.
Decided from code: yes, for pipeline files in the repository.

### [IEC 62443 SM-8] Private keys used for signing and identity are controlled
Look for: private keys, certificates with private parts, or signing credentials committed to the repository, firmware images or build logs. A signing step that uses a key from an unprotected variable. A key shared across products.
Decided from code: yes.

### [IEC 62443 SD-1] Design follows secure design principles
Look for: sensitive functions reachable without authentication, shared admin accounts, trust placed in data from the network or other zones, default open services, and security decisions made in the client only. Authorisation done in some code paths but not others.
Decided from code: yes.

### [IEC 62443 SD-4] Secure design practices are followed for the technology used
Look for: known unsafe patterns for the platform, such as plain-text protocols where secure ones are available, home-made cryptography, and custom authentication where the platform offers a proven one. Unused services and ports left enabled.
Decided from code: yes.

### [IEC 62443 SI-1] Security implementation review findings are not hidden
Look for: new suppressions of static analysis or security lint findings with no reason. Review or analysis steps removed from the pipeline. Code that looks like a backdoor: hidden admin switches, hard-coded bypass values, or deliberately obscured logic.
Decided from code: yes.

### [IEC 62443 SI-2] Secure coding standards are followed
Look for: unsafe functions (`strcpy`, `gets`, `eval` on input), unchecked buffer sizes, integer overflow in size calculations, injection, unchecked return values, hard-coded credentials, and compiler warnings or hardening flags turned off. Coding-rule checks removed from the build.
Decided from code: yes, where the project names its coding standard.

### [IEC 62443 SVV-1] Security requirements are tested
Look for: changes to authentication, authorisation, logging, cryptography or input handling with no tests of the failure cases, such as wrong user, expired credential or malformed message. Security tests deleted, skipped or weakened.
Decided from code: yes.

### [IEC 62443 SVV-3] Vulnerability testing is kept in the pipeline
Look for: fuzz tests, dynamic scans or dependency scans removed, set to continue on failure, or limited by new exclusions. New parsers or protocol handlers with no tests of malformed input.
Decided from code: partly. Testing done outside the repository isn't visible.

### [IEC 62443 SUM-4] Security updates are delivered in a way that can be trusted
Look for: update packages installed with no signature or version check, update channels without TLS, rollback protection removed, or checks that fail open. Update keys held in the product in a way that lets anyone sign updates.
Decided from code: yes.

### [IEC 62443 CR 1.1] Human users are identified and authenticated
Look for: interfaces that give users access, such as web, CLI, local or fieldbus tools, with no sign-in. Authentication that can be skipped through another path. Access based only on network location.
Decided from code: yes.

### [IEC 62443 CR 1.5] Authenticators are stored and managed safely
Look for: passwords stored in plain text or with fast hashes. Default or fixed passwords, tokens or keys. Authenticators that can't be changed, or that are logged or shown back.
Decided from code: yes.

### [IEC 62443 CR 2.1] Authorisation is enforced on every path
Look for: functions or resources reachable with no permission check. Checks done only in the user interface. Roles or privileges widened. Sibling handlers missing the check that others have.
Decided from code: yes.

### [IEC 62443 CR 2.8] Security-relevant events are logged
Look for: removal of logs for sign-in attempts, permission failures, configuration changes, updates, or privileged actions. Logs that include secrets or leave out who and when.
Decided from code: yes.

### [IEC 62443 CR 3.4] Software and data integrity is checked
Look for: firmware, configuration or update files used with no integrity check. Integrity checks removed or made optional. Weak checksums used where a cryptographic check is needed.
Decided from code: yes.

### [IEC 62443 CR 3.5] Input is validated
Look for: data from networks, fieldbuses, files, or users used with no check of type, length, range or format. Parsers with no limits. Validation removed or moved only to a client.
Decided from code: yes.

### [IEC 62443 CR 3.7] Errors don't reveal internals
Look for: error messages, stack traces, or protocol responses that give paths, versions, configuration or key material. Errors that are ignored and leave the component in an unsafe state.
Decided from code: yes.

### [IEC 62443 CR 4.3] Cryptography is sound and keys are handled safely
Look for: weak or obsolete algorithms, short keys, static IVs or nonces, home-made crypto, certificate checks turned off, random numbers from a non-cryptographic source, and keys shared across all devices. Secrets in source or firmware images.
Decided from code: yes.

### [IEC 62443 CR 7.7] Only the needed functions, ports and services are enabled
Look for: new open ports, protocols, services, test modes, demo accounts or debug interfaces that are on in release builds. Services that were off by default now on.
Decided from code: yes.
