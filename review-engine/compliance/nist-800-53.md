# NIST SP 800-53 Rev. 5: code review checklist

Source: NIST SP 800-53 Rev. 5, Security and Privacy Controls for Information Systems and Organizations (September 2020, with updates through Release 5.2.0), https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final. The checks below are written in our own words. The IDs are the catalogue's control and enhancement IDs, so a finding can be traced back to the official text.

SP 800-53 is a catalogue of controls that organisations pick from, usually through a baseline (low, moderate or high) or an overlay. Many controls are about policy and operations. The checks below are the controls whose evidence can show up in code, configuration, dependencies or pipelines. Which controls apply to a given system, and with what settings, is decided by the organisation, so where a setting is a number (such as a lockout limit or timeout), flag a missing mechanism and say a person must confirm the required value.

## When this applies

Apply these checks to changes in application code, dependencies and lockfiles, infrastructure and deployment configuration, CI/CD pipelines, and security features such as sign-in, permissions, cryptography and logging.

If the change touches none of the areas above, such as documentation, styling or copy, report this standard as `not_applicable`.

## Checks

### [NIST 800-53 AC-3] Access is enforced on every request
Look for: new endpoints, queries, jobs or exports that return or change data without checking the caller's permission. Object IDs taken from the request and used with no ownership check. Authorisation done only in the client. Checks that can be skipped by another route or method.
Decided from code: yes.

### [NIST 800-53 AC-6] Accounts and code get only the access they need
Look for: wildcard or admin-level roles and IAM actions where a narrow one would do. Services that run as root or with wide database rights. Tokens and API scopes broader than the feature needs. Privileged functions reachable by ordinary roles.
Decided from code: yes, for what the code and infrastructure files grant.

### [NIST 800-53 AC-7] Repeated failed sign-ins are limited
Look for: sign-in, password reset, one-time code or API key endpoints with no lockout, delay or rate limit. Limits removed or raised without reason. Different error messages that reveal whether an account exists.
Decided from code: partly. The exact limit is a local setting, so say a person must confirm it.

### [NIST 800-53 AC-12] Sessions end
Look for: sessions or tokens that never expire, expiry raised to days or removed, logout that doesn't invalidate the session or refresh token on the server, tokens that stay valid after a password change.
Decided from code: partly. Required timeout values are set by the organisation.

### [NIST 800-53 IA-2] Users are identified and authenticated, with multi-factor for sensitive access
Look for: sign-in flows without a second factor for admin or sensitive actions where the project expects one. Multi-factor authentication that can be bypassed with a flag or fallback. Shared logins used by several people.
Decided from code: yes, for what the code enforces. Which accounts must use multi-factor is a policy decision.

### [NIST 800-53 IA-5] Authenticators are created, stored and handled safely
Look for: passwords stored in plain text or hashed with MD5, SHA-1 or unsalted SHA-256 instead of bcrypt, scrypt, Argon2 or PBKDF2. Default or hard-coded credentials. API keys or tokens committed to the repository, shown in logs or returned after creation. Reset tokens that are guessable or never expire. Weak password rules, or password checks removed.
Decided from code: yes.

### [NIST 800-53 AU-2] Security-relevant events are logged
Look for: sign-in and failures, permission changes, data export or deletion, admin actions and configuration changes that write no audit event. Logging turned off or lowered in production. Events logged in one code path but missed in another.
Decided from code: yes. Which events the organisation has chosen to log is a local decision, so compare with similar code in the project.

### [NIST 800-53 AU-3] Log records say what happened, to whom and when
Look for: audit events missing the time, event type, outcome, acting user or service, source address or the object affected. Log lines that are free text and can't be searched. Secrets, tokens or whole sensitive records written into logs.
Decided from code: yes.

### [NIST 800-53 AU-9] Audit logs are protected
Look for: logs the application can edit or delete, log files with open permissions, log storage that any service can write over, logs shipped over an unencrypted channel, or a change that lets users view others' logs.
Decided from code: partly. Storage permissions may be set outside the repository.

### [NIST 800-53 CM-6] Configuration uses secure settings
Look for: debug mode, verbose errors, default credentials, open admin interfaces, permissive CORS, disabled security headers or disabled certificate checks in configuration that reaches production. Settings that differ from the project's hardening baseline.
Decided from code: yes, for configuration in the repository.

### [NIST 800-53 SC-8] Data in transit is protected
Look for: plain HTTP, FTP, or unencrypted database, cache and queue connections. TLS verification disabled. Old protocol versions allowed. Sensitive values in URLs. Internal service traffic sent unencrypted where the project encrypts it elsewhere.
Decided from code: yes.

### [NIST 800-53 SC-12] Cryptographic keys are managed
Look for: keys, salts or secrets hard-coded or committed, stored beside the data they protect, reused across environments, generated from weak sources, or with no way to rotate. Keys read from a key management service or secret store are the better design.
Decided from code: partly. Key lifecycle practices outside the repository can't be seen.

### [NIST 800-53 SC-13] Cryptography uses approved algorithms
Look for: MD5, SHA-1, DES, 3DES, RC4, ECB mode, small RSA keys, home-made encryption, non-cryptographic random numbers used for keys, tokens or IVs. A requirement for validated modules (FIPS) should be checked against the organisation's rules.
Decided from code: partly. Whether a validated module is needed depends on the system's rules.

### [NIST 800-53 SC-28] Stored data is protected
Look for: new tables, files, caches, queues or buckets with sensitive data and no encryption at rest, public or broad read access, or encryption keys held next to the data.
Decided from code: partly. Platform encryption settings may live outside the repository.

### [NIST 800-53 SI-2] Flaws are found and fixed
Look for: known-vulnerable dependencies, runtimes or base images added or pinned back. Automated update tools or scans removed or ignored. Unmaintained packages with no replacement plan. Security patches reverted.
Decided from code: yes, for what the repository declares.

### [NIST 800-53 SI-7] Software and data integrity is checked
Look for: downloaded code, plug-ins, updates or images used without checksum or signature verification. Lockfile integrity hashes removed. Mutable image tags. Unsigned or unverified build artefacts. Stored records or files whose tampering would go unnoticed.
Decided from code: yes.

### [NIST 800-53 SI-10] Input is validated
Look for: request data, files, headers, URLs or messages used without checking type, length, range or format. Queries built by string joining. Paths, commands or templates built from input. Validation done only in the client.
Decided from code: yes.

### [NIST 800-53 SI-11] Errors don't reveal sensitive details
Look for: stack traces, SQL, file paths, internal hostnames, tokens or personal data returned to users or written to logs in error handlers. Catch blocks that hide failures, so security errors go unnoticed.
Decided from code: yes.

### [NIST 800-53 SA-11] Developer testing covers security
Look for: security-relevant changes (authorisation, input handling, cryptography) with no tests. Static analysis, dependency checks or security tests removed or made non-blocking in the pipeline. Failing security tests skipped.
Decided from code: partly. Penetration tests and the quality of the review are outside the repository.

### [NIST 800-53 SR-3] Supply chain controls cover third-party components
Look for: new dependencies, actions, images or build tools from unknown publishers, installed from unofficial sources, unpinned, or run with install scripts. Build steps that fetch and run code from the internet. Dependency sources changed without reason.
Decided from code: partly. Supplier vetting and contracts are outside the repository.
