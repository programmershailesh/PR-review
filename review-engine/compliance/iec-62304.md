# IEC 62304: code review checklist

Source: International Electrotechnical Commission, IEC 62304:2006+AMD1:2015 CSV, Medical device software, Software life cycle processes, https://www.iso.org/standard/64686.html. The standard is paid for and protected by copyright. The checks below are written in our own words and cite clause numbers only, so a finding can be traced to the official text. Clause numbers are the standard's own. The main clauses (such as 5.2 or 8.1) were checked against a public preview of the 2006 edition's contents; the third-level numbers and the safety classes rest on secondary public listings, not on the standard's text.

IEC 62304 describes the life cycle processes for software in medical devices, including software that is itself a medical device. Requirements depend on the software safety class (A: no injury possible, B: non-serious injury possible, C: death or serious injury possible). The class is assigned in risk management, so code review can't decide it.

## When this applies

Apply these checks to changed code of software that is, or is part of, a medical device, or that supports one. Signs include a medical device or SaMD label, a safety class in the repository, risk or hazard files, design history documents, clinical or diagnostic algorithms, dosing, alarm or monitoring logic, and device firmware.

State the safety class the project claims, if known. Say which checks apply to that class and which don't. Many items below apply only to class B or C. If the project doesn't develop medical device software, report this standard as `not_applicable`.

## Checks

### [IEC 62304 5.1.1] A software development plan exists and covers the work
Look for: a repository for medical device software with no development plan or process document, or changes that add new components, tools or activities the plan doesn't mention.
Decided from code: partly. The plan is a document, so ask a person to confirm it is current.

### [IEC 62304 5.2.2] Software requirements are written down and cover functions, performance, interfaces and safety needs
Look for: behaviour added or changed with no linked requirement, requirements files that are not updated with the change, requirement IDs that no test or code refers to. Missing items such as inputs, outputs, alarms or data definitions in the requirements the change affects.
Decided from code: partly. Requirement quality needs a human reader.

### [IEC 62304 5.2.3] Risk control measures appear in the software requirements
Look for: safety-related behaviour (limits, interlocks, alarms, confirmation steps, fail-safe states) added in code with no matching requirement, or requirements that cite a risk control but have no implementation or test.
Decided from code: partly. This applies to class B and C.

### [IEC 62304 5.3.1] Requirements are turned into a documented software architecture
Look for: new components, services or interfaces with no architecture update, changes that go around the documented structure, interfaces between items that are not described.
Decided from code: partly. This applies to class B and C.

### [IEC 62304 5.3.5] Parts needed for risk control are kept separate from other parts
Look for: safety-critical logic that shares memory, a process, a database or a failure path with non-critical code. Changes that let non-critical code call into or change safety-critical state. Missing isolation the architecture says is required.
Decided from code: partly. This applies to class C.

### [IEC 62304 5.5.3] Software units have acceptance criteria and are checked against them
Look for: units with no tests or defined checks, unit tests removed or skipped, thresholds or assertions loosened, safety-related units without boundary and error-case tests.
Decided from code: yes, for tests in the repository. This applies to class B and C.

### [IEC 62304 5.6.3] Integration is tested
Look for: new interfaces between units or components with no integration tests, integration tests removed, mocks that hide the real interface behaviour for safety-related paths.
Decided from code: yes, for tests in the repository. This applies to class B and C.

### [IEC 62304 5.7.1] Tests exist for each software requirement
Look for: requirements with no test, tests that do not name the requirement they verify, test results not kept by the pipeline, system tests removed or disabled.
Decided from code: partly. Traceability may be kept in a separate tool.

### [IEC 62304 5.7.3] Changes are retested
Look for: changes to validated or safety-related code merged without the related tests being run or updated, pipelines that let release proceed with failing or skipped tests.
Decided from code: yes, for what the pipeline enforces.

### [IEC 62304 5.8.4] Released versions are identified and documented
Look for: builds with no version stamp, version numbers not tied to a commit or tag, release artifacts that can't be traced to their source, a release process that overwrites an earlier version.
Decided from code: yes.

### [IEC 62304 7.1.3] Published problem lists for third-party software are evaluated
Look for: third-party components added or updated where the supplier's published list of known defects, or an advisory, shows a relevant problem and nothing records how it was assessed. Dependency scanning removed from the pipeline.
Decided from code: partly. The evaluation record sits outside the repository. This applies to class B and C.

### [IEC 62304 7.4.1] Changes are analysed for their effect on safety
Look for: changes to safety-related code, thresholds, alarms or algorithms with no sign of impact analysis, no linked risk file update, or no risk reviewer on the change.
Decided from code: partly. A person must confirm the analysis was done.

### [IEC 62304 8.1.2] Software of unknown provenance (SOUP) is identified
Look for: third-party libraries, operating systems or frameworks added without being listed in the SOUP list or bill of materials, with title, manufacturer and version. Unpinned versions (`^`, `latest`, floating base images) that make the exact version unknown.
Decided from code: yes, for dependency files and lock files.

### [IEC 62304 8.2.1] Changes are requested and approved before they are made
Look for: changes that bypass review or approval, direct commits to release branches, change requests that have no link to a problem report or a requirement.
Decided from code: partly. Approval records may live in the hosting platform or an issue tracker.

### [IEC 62304 8.2.4] Changes can be traced
Look for: commits with no reference to a ticket or change request, squashed or rewritten history on release branches, changes that can't be linked back to a requirement or problem report.
Decided from code: partly.

### [IEC 62304 9.1] Problems are reported and recorded
Look for: error handling that swallows safety-related failures with no log or report, removal of error reporting, fixes with no linked problem report.
Decided from code: partly. The problem tracking process is outside the repository.
