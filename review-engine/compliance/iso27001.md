# ISO/IEC 27001:2022 Annex A: code review checklist

Source: ISO/IEC 27001:2022, Information security, cybersecurity and privacy protection: Information security management systems: Requirements, Annex A, https://www.iso.org/standard/27001. ISO/IEC 27002:2022 gives the guidance for each Annex A control. The checks below are written in our own words. The numbers are Annex A's control numbers, so a finding can be traced back to the official text.

Annex A has 93 controls in four groups: organisational (A.5), people (A.6), physical (A.7) and technological (A.8). This checklist uses the technological controls, plus the few organisational ones that code can show. Each organisation records which Annex A controls apply to it in its Statement of Applicability, so a control here may have been left out on purpose.

## When this applies

Apply these checks to changed code in systems inside the organisation's ISO 27001 scope. Signs of this include sign-in and permission code, personal or confidential data handling, cryptography, logging, configuration files, infrastructure code, dependencies, test data and CI/CD pipelines.

The code can't show the scope or the Statement of Applicability. If a check fails, report it, and say in the status note that a person should confirm the control applies.

Ordinary bugs with no security effect belong to the main review. If the change touches none of the areas above, such as documentation, styling or copy, report this standard as `not_applicable`.

## Checks

### [ISO 27001 A.5.17] Passwords, keys and tokens are handled safely
Look for: credentials, API keys, private keys or tokens written into source code, scripts or committed configuration files. Passwords stored in plain text, or hashed with fast hashes such as MD5 or SHA-1 instead of bcrypt, scrypt, Argon2 or PBKDF2. Default or shared passwords created by code or seed data that would ship to production. Passwords or tokens put in URLs, emails or logs. Reset or invite tokens that never expire or can be used more than once.
Not a breach: placeholders, and values read from environment variables or a secret manager.
Decided from code: yes.

### [ISO 27001 A.5.34] Personal data is collected and handled only as allowed
Look for: new collection of personal data beyond what the feature needs. Personal data sent to new third parties, analytics tools or AI services. Personal data kept with no retention limit. Code that skips consent or opt-out settings the project already has.
Decided from code: partly. Which laws and contracts apply is outside the repository.

### [ISO 27001 A.8.2] Admin and other privileged access is limited and controlled
Look for: new admin roles or superuser flags without a narrow check. Service accounts, IAM roles or database users given admin or wildcard rights. Privileged actions, such as impersonating a user, changing roles, exporting data or changing settings, that leave no audit record. Hidden parameters, headers or values that grant admin access.
Decided from code: partly. Who holds privileged roles is managed outside the repository.

### [ISO 27001 A.8.3] Users can reach only the data and functions they're allowed to
Look for: records loaded by ID with no owner or tenant check. Queries that skip the tenant filter. Role checks done only in the UI. API responses that return fields the caller isn't allowed to see. A user ID, role or tenant taken from a client header, body or cookie and trusted without checking it.
Decided from code: yes.

### [ISO 27001 A.8.4] Source code and build tools are protected from unwanted access
Look for: source maps, `.git` folders or source archives served from production. Repository permissions, deploy keys or CI tokens given wider write access in infrastructure code or pipeline files. `CODEOWNERS` entries for sensitive paths removed.
Decided from code: partly. Repository access settings usually live in the Git host.

### [ISO 27001 A.8.5] Sign-in is secure
Look for: sign-in endpoints with no rate limit, lockout or delay after failed attempts. Error messages that reveal whether the username or the password was wrong. Session tokens that are predictable, never expire, or aren't replaced after sign-in. Multi-factor authentication removed, or made skippable for admin users or sensitive actions.
Decided from code: partly. Identity provider settings may be outside the repository.

### [ISO 27001 A.8.8] Known vulnerabilities in dependencies are dealt with
Look for: new or upgraded dependencies, base images or tools with known vulnerabilities. Versions held at an old release when a fix has been published. Dependency or image scanning removed from CI or set to never fail. Packages that are no longer maintained.
Decided from code: partly. Patching timelines and scans run outside CI aren't visible in the repository.

### [ISO 27001 A.8.9] Security settings follow a known, secure baseline
Look for: debug mode, detailed errors or test features turned on in production configuration. Default passwords or sample keys left in place. Infrastructure code that turns off encryption or logging, removes public access blocks, or makes storage public. Settings changed by one-off scripts instead of through the project's configuration files.
Decided from code: yes, for configuration in the repository.

### [ISO 27001 A.8.10] Data is deleted when it's no longer needed
Look for: delete or account closure features that leave copies in caches, search indexes, object storage, logs or derived tables. New stores of personal or confidential data with no expiry or clean-up job. Soft delete where real deletion is promised.
Decided from code: partly. Retention periods and backup expiry are usually set outside the repository.

### [ISO 27001 A.8.11] Sensitive data is masked where the full value isn't needed
Look for: screens, API responses, exports, logs or support tools that show full identity numbers, card numbers, account numbers or contact details when a partial value would do. Production data copied to test or analytics systems without masking or pseudonymisation.
Decided from code: yes, for what the code shows or copies.

### [ISO 27001 A.8.12] Sensitive data doesn't leak to places it shouldn't go
Look for: personal or confidential data sent to error trackers, analytics, logs, AI services or other third parties. API responses that return whole database records instead of chosen fields. Debug endpoints that dump internal state. Public storage buckets, or shared links that never expire.
Decided from code: yes.

### [ISO 27001 A.8.15] Security events are logged, and the logs are protected
Look for: sign-ins, failed sign-ins, permission changes, admin actions and data exports that write no log. Log entries that leave out who, what, when or the outcome. Passwords, tokens, keys or full personal data written to logs. Logs that ordinary users, or code paths they control, can change or delete.
Decided from code: yes, for what the code logs.

### [ISO 27001 A.8.19] Software is installed on running systems only in a controlled way
Look for: containers or servers that install packages when they start (`pip install`, `npm install` or `apt-get install` in an entrypoint script). `curl ... | sh` in Dockerfiles or setup scripts. Installs from unpinned versions, unofficial registries or plain HTTP. Features that let users or plugins install software at run time.
Decided from code: partly. Servers managed outside the repository can't be checked.

### [ISO 27001 A.8.20] Network rules only open what's needed
Look for: security groups, firewall rules, network policies or Kubernetes services opened to `0.0.0.0/0` or `::/0`. Database, cache, admin or metrics ports reachable from the internet. Network policies between services removed.
Decided from code: yes, for network rules in the repository. A cloud console or another repository may hold the rest.

### [ISO 27001 A.8.24] Cryptography is used correctly
Look for: weak or broken algorithms, such as MD5 or SHA-1 for security purposes, DES, RC4, ECB mode, or RSA keys under 2048 bits. Fixed or reused IVs and nonces. Keys stored in code or next to the data they protect. Non-cryptographic random functions (`Math.random`, `random.random`, `rand()`) used for tokens, IDs or keys. TLS verification turned off, or old TLS versions allowed. Home-made encryption schemes.
Decided from code: partly. Key management outside the repository can't be checked.

### [ISO 27001 A.8.28] Code is written to resist common attacks
Look for: SQL, NoSQL, command, LDAP or template injection from unchecked input. Cross-site scripting from output that isn't escaped. Unsafe deserialisation of untrusted data. Path traversal in file access. Server-side request forgery from user-supplied URLs. Errors that show stack traces or internal details to users. New suppressions of security linter warnings with no reason given.
Decided from code: yes.

### [ISO 27001 A.8.29] Security features are tested before release
Look for: changes to sign-in, permissions, cryptography or input handling with no tests of the security behaviour, including failure cases such as the wrong user, an expired token or bad input. Security tests deleted, skipped (`skip`, `xit`, `@Ignore`, `@Disabled`) or changed so they always pass. Security test or scan stages removed from CI.
Decided from code: yes.

### [ISO 27001 A.8.31] Development, test and production are kept apart
Look for: production URLs, credentials or database connections in development or test configuration. Test or staging code that can run against production. Debug endpoints, test users or flags that bypass security, shipping to production. One set of credentials shared across environments.
Decided from code: yes, for configuration in the repository.

### [ISO 27001 A.8.32] Changes go through a controlled process
Look for: pipeline changes that deploy without the usual tests, review or approval. Required jobs removed, or `continue-on-error: true` added to checks. Scripts that change production by hand, outside the pipeline. Branch protection weakened in infrastructure code.
Decided from code: partly. Approval rules usually live in the Git host's settings.

### [ISO 27001 A.8.33] Test data doesn't expose real information
Look for: real personal data, customer records, production dumps or real credentials in fixtures, seed files, snapshots or sample configuration. Test data copied from production without masking.
Not a breach: clearly fake data, such as generated names and `example.com` addresses.
Decided from code: yes.
