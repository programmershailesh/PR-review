# OWASP Top 10 (2025 edition): code review checklist

Source: OWASP Foundation, OWASP Top 10:2025 (final release), https://owasp.org/Top10/2025/. The OWASP Top 10 is © The OWASP Foundation and licensed under Creative Commons Attribution-ShareAlike 4.0 (CC BY-SA 4.0, https://creativecommons.org/licenses/by-sa/4.0/). The checks below are written in our own words, based on that work. The IDs are the list's own category IDs, so a finding can be traced back to the official text.

The Top 10 is a list of the most serious risks to web applications. Each category is broad, so each check gathers the code patterns that belong to it. The 2025 edition renumbered the list. For example, injection is A05:2025 (it was A03 in 2021), and server-side request forgery is now part of A01:2025. Always cite the 2025 IDs exactly as written in the headings.

## When this applies

Apply these checks to changed code in a web application, a web API or the services behind them. This includes request handlers, data access, sign-in and sessions, templates and front-end code, security settings, dependency manifests and build pipelines.

Desktop apps, command-line tools and background jobs can still break A03, A04, A05, A08, A09 and A10, so apply those checks even when there is no web layer. Report this standard as `not_applicable` only when the change has no security-relevant code, such as documentation, copy text, styling, or tests that don't change behaviour.

## Checks

### [OWASP Top 10 A01:2025] Users can only reach the data and actions they are allowed to
Look for: new routes, controllers, resolvers or handlers with no authorisation check, or a check done only in the browser. Records loaded by an ID from the request without checking that the caller owns them or may see them, such as `findById(req.params.id)` with no owner or tenant filter. Write methods (POST, PUT, PATCH, DELETE) that are less protected than the matching read. Roles or user IDs taken from the request body, a hidden field or an unverified cookie. CORS that allows any origin, or reflects the request origin, on endpoints that use cookies or return private data. Cookie-authenticated actions that change state with no CSRF protection. Server-side requests to URLs the user supplies, with no allow list of hosts and schemes, which can reach internal services or cloud metadata (server-side request forgery). File paths built from user input without blocking `../` (path traversal). Redirects to a URL taken from the request without an allow list. Directory listing, `.git` folders or backup files served from the web root.
Not a breach: resources that are meant to be public, such as a marketing page or a public product list.
Decided from code: yes, for checks made in code. Rules enforced by a gateway or identity provider outside the repository need a person to confirm.

### [OWASP Top 10 A02:2025] Security settings are hardened and nothing unneeded is switched on
Look for: debug modes turned on in production settings, such as `DEBUG = True` in Django, `app.run(debug=True)`, the ASP.NET developer exception page outside development, or Spring Boot actuator endpoints exposed without protection. Default accounts or passwords in config files, seed data or container images. Passwords and static keys in configuration files or pipeline definitions, where the platform offers short-lived credentials or role-based access instead. Sample apps, test pages, admin consoles or unused ports left enabled. Security headers removed or weakened. Session cookies set without `Secure` or `HttpOnly`. XML parsers that resolve external entities or expand nested entities (XXE). Cloud storage made public, such as an S3 bucket with a `public-read` ACL, or IAM policies with `*` for actions or resources.
Not a breach: debug settings in files that only apply to local development and can't reach production.
Decided from code: partly. Settings in this repository can be checked. Settings made in a cloud console or by a platform team are outside it.

### [OWASP Top 10 A03:2025] Dependencies and the build pipeline can be trusted
Look for: new dependencies added without a matching lockfile change. Packages pulled from unofficial registries, Git URLs or copied-in vendor folders with no version. Dependencies that are unmaintained or have known serious vulnerabilities. Package names that look like typos of popular ones. CI/CD changes that use third-party actions or images by a moving tag (`uses: some/action@main`, `image: tool:latest`), run pull request code with access to secrets (for example `pull_request_target` that checks out the PR head), give the pipeline more permissions than it needs, or skip review or branch protection steps. Secrets committed to the repository.
Not a breach: version ranges in a library's own manifest, which is normal, as long as the application that ships it commits a lockfile.
Decided from code: partly. Whether a version has a known vulnerability needs a scanner or advisory database. Registry and CI settings may live outside the repository.

### [OWASP Top 10 A04:2025] Sensitive data is protected with strong, correctly used cryptography
Look for: sensitive data sent over plain HTTP, FTP or unencrypted email. TLS certificate checks turned off (`verify=False`, `rejectUnauthorized: false`, `InsecureSkipVerify: true`, a trust-all `TrustManager`). MD5 or SHA-1 used for a security purpose. Weak ciphers or modes such as DES, RC4 or ECB, or RSA without OAEP padding. Encryption with no integrity check, where authenticated encryption such as AES-GCM fits. Fixed, reused or predictable IVs and nonces. Encryption keys hard-coded or committed to the repository. Passwords used directly as keys without a key derivation function. Passwords stored in plain text, encrypted instead of hashed, or hashed with a fast or unsalted hash instead of a slow password hash such as Argon2, scrypt or PBKDF2. Non-cryptographic random generators (`Math.random`, `java.util.Random`, Python's `random`) used for tokens, keys or reset codes, or a secure generator given a fixed seed. Responses with sensitive data that a CDN, proxy or app cache may store.
Not a breach: MD5 or SHA-1 used only where security doesn't depend on it, such as cache keys or file deduplication.
Decided from code: yes, for what the code does and configures. How keys are stored and rotated outside the repository needs a person to check.

### [OWASP Top 10 A05:2025] Untrusted input can't change the meaning of a query, command or page
Look for: SQL, NoSQL, LDAP, XPath or ORM queries built by joining strings with request data, such as `"SELECT ... WHERE id=" + id`, f-strings or template literals in queries, `knex.raw` or `Sequelize.literal` with user values, `FromSqlRaw` with string concatenation, or MongoDB `$where` with user input. Table or column names taken from input without an allow list. Shell commands built from input (`os.system`, `subprocess` with `shell=True`, `child_process.exec`, `Runtime.exec` with one string). `eval`, `new Function`, expression languages (SpEL, OGNL) or server-side templates (`render_template_string`) fed with user input. Cross-site scripting: user data written into pages without encoding, through `innerHTML`, `dangerouslySetInnerHTML`, `v-html`, `|safe`, `Html.Raw` or `th:utext`. User input placed in HTTP headers without stripping line breaks. Stored procedures that build SQL with `EXEC` or `EXECUTE IMMEDIATE`.
Not a breach: parameterised queries, ORM query builders with bound values, framework templates that encode by default, and argument arrays passed to a process without a shell.
Decided from code: yes.

### [OWASP Top 10 A06:2025] Business rules and abuse cases are built into the design
Look for: flows that trust the client to enforce rules, such as a checkout that accepts a price or discount from the request, or a multi-step flow where a later step doesn't check that the earlier steps passed. No plausibility checks, such as negative quantities or amounts over a limit. No limits on actions that cost money or can be abused, such as sign-ups, coupon redemption, sending SMS or booking slots. Two requests that can spend the same balance or book the same slot at once (race conditions). Uploads accepted without checking the file type. Tenants not kept apart at every layer. New sensitive flows with no tests for misuse.
Decided from code: partly. The code shows how the flow is built. Whether the design has a threat model or agreed requirements is outside the repository.

### [OWASP Top 10 A07:2025] Only the real user can sign in, and sessions end when they should
Look for: login, sign-up, password reset or one-time code endpoints with no rate limit, lockout or other brute-force protection. Hard-coded or default credentials, especially for admin users. Password rules that accept very weak or known-breached passwords. Different messages, status codes or timings that reveal whether an account exists. "Secret questions" or other knowledge-based answers for recovery. A second factor that can be skipped through a fallback path. Session IDs placed in URLs, or not replaced with a new one after login. Sessions or tokens that aren't invalidated on logout, or have no idle or absolute timeout. Tokens accepted without checking their signature, expiry, issuer (`iss`), audience (`aud`) or scope. Authentication based on an IP address or the `Referer` header.
Decided from code: yes, for code in this repository. Settings in an external identity provider are outside it.

### [OWASP Top 10 A08:2025] Code and data are checked before they are trusted
Look for: untrusted data deserialised with formats that can create arbitrary objects, such as `pickle.loads`, `yaml.load` without a safe loader, Java `ObjectInputStream`, .NET `BinaryFormatter` or PHP `unserialize`, on data from users, cookies, files or queues. Cookies or client-side state trusted for security decisions without a signature or MAC. Auto-update or plugin code that downloads and runs code without checking a signature or hash. Scripts loaded from a CDN or other domain without subresource integrity. CI steps that fetch code or artifacts from untrusted places without verifying them. Request data copied straight onto objects so a caller can set fields they shouldn't, such as `role` or `isAdmin` (mass assignment).
Decided from code: yes.

### [OWASP Top 10 A09:2025] Security events are logged safely and can raise alerts
Look for: new sign-in, access control or input validation failures, or high-value transactions, that aren't logged. Logging that records success but not failure. Passwords, tokens, session IDs, card numbers or other personal data written to logs. User input written to logs without encoding, so line breaks can forge entries (log injection). Errors caught and dropped without a log entry. Audit records stored where the application can change or delete them. Log or alert details shown to users.
Decided from code: partly. The code shows what is logged. Monitoring, alerting, retention and log protection are usually set up outside the repository.

### [OWASP Top 10 A10:2025] Errors and unusual conditions are handled safely and fail closed
Look for: empty `catch` blocks, or broad catches that carry on as if nothing happened. Error paths that grant access or finish a transaction (failing open), such as treating an error from the permission service as "allowed". Multi-step transactions with no rollback when one step fails. Unchecked return values or null results from security-relevant calls. Missing parameters or extra parameters that the code doesn't handle. Error responses that show stack traces, queries, internal paths or secrets. No global handler for unhandled exceptions or promise rejections. Missing limits that let one request exhaust memory, threads, connections or a paid quota, such as no timeouts, no maximum sizes, or unbounded loops and retries.
Not a breach: catching an error, logging it, and returning a safe, generic message.
Decided from code: yes.
