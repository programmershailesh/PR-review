# ISO/SAE 21434:2021 cybersecurity engineering: code review checklist

Source: ISO/SAE 21434:2021, Road vehicles, Cybersecurity engineering (first edition, August 2021), https://www.iso.org/standard/70918.html. The checks below are written in our own words. The IDs are clause numbers of the standard, so a finding can be traced back to the official text. Only clause numbers that are published in the standard's structure are used, mostly at the clause level and at 8.3 to 8.6 and 5.4.1.

The standard sets out how a vehicle supplier or maker manages cybersecurity risk over the life of an item: organisation and project management (clauses 5 and 6), shared work between customer and supplier (7), continual activities such as monitoring and vulnerability handling (8), concept (9), product development (10), validation (11), production (12), operations and maintenance (13), end of support (14), and threat analysis and risk assessment methods (15). Most of it is about process and records. The checks below are the ones where evidence shows up in code, configuration, dependencies and pipelines.

## When this applies

Apply these checks to changes in software and configuration for road-vehicle electrical and electronic systems and their back-end services: application and embedded code, communication interfaces, diagnostic and update functions, key and certificate handling, dependencies, build and release pipelines. If the change touches none of these (for example documentation or styling), report this standard as `not_applicable`.

## Checks

### [ISO 21434 5.4.1] Cybersecurity rules of the organisation are not bypassed by the pipeline
Look for: security checks, reviews or scanners in the build pipeline removed, set to continue on failure, or skipped for some branches. Required reviewers or protected-branch settings loosened in repository settings files.
Decided from code: partly. Policies and rules are defined outside the repository.

### [ISO 21434 6] Cybersecurity work for the item is traceable in the repository
Look for: security-related requirements, threat IDs or cybersecurity goals referenced in code or tests that no longer exist, or removed with no replacement. Security-related behaviour changed with no reference to its requirement, in a project that links them.
Decided from code: partly. The plan and the case are kept in other documents.

### [ISO 21434 7] Interfaces to other suppliers and components keep their agreed security behaviour
Look for: changes to message formats, authentication or key exchange with another party's component that skip checks the interface needs. Shared secrets or test keys shared across suppliers. Relaxed validation of data received from another supplier's component.
Decided from code: partly. The agreement itself is outside the repository.

### [ISO 21434 8.3] Cybersecurity information can be collected from the product
Look for: removal of security event logging, error counters, or reporting hooks that feed monitoring. Logs that drop failed authentication, failed updates or diagnostic access attempts. Telemetry paths removed with no replacement.
Decided from code: partly. How information is used by monitoring teams is outside the code.

### [ISO 21434 8.5] Known weaknesses in the software and its components are found and not hidden
Look for: dependencies and components with known vulnerabilities, or past end of support. Dependency or vulnerability scanning removed from CI, or set to continue on failure. New suppressions of security findings with no reason.
Decided from code: yes, for the dependencies and scans in the repository.

### [ISO 21434 8.6] Vulnerabilities are managed, and fixes reach the whole code base
Look for: a security fix applied in one place while the same unsafe pattern remains in sibling code. Fixes with no test that catches the problem coming back. Vulnerability records or advisories in the repository left open with no owner. Apply this check mainly when the change is itself a security fix.
Decided from code: partly. Tracking and prioritisation happen in other tools.

### [ISO 21434 9] Cybersecurity goals from the concept stay valid in the implementation
Look for: removal or weakening of controls that protect assets named in the project, such as signing keys, personal data, vehicle control commands or diagnostic access. New external interfaces (radio, USB, OBD, cloud APIs) added with no authentication or access limits.
Decided from code: partly. The assets and goals come from the project's concept documents.

### [ISO 21434 10] Software and interfaces are designed, built and tested with security in mind
Look for: input from buses, radio, diagnostics or networks used without length and range checks. Memory-unsafe functions, injection and parsing without limits. Debug or test interfaces left on in release builds (open UART, JTAG, unauthenticated diagnostic commands). Hard-coded credentials or keys, fixed seeds, weak or obsolete cryptography, certificate checks turned off, and the same key on every device. Sensitive functions (update, key provisioning, remote commands) with no authentication. Updates or boot images installed with no signature or rollback check. Dependencies with no version pin or integrity hash. New security-relevant code with no tests of invalid or malicious input, or fuzz and security tests removed.
Not a breach: test fixtures that can't reach production devices.
Decided from code: yes.

### [ISO 21434 12] Production and release steps handle secrets and debug access safely
Look for: factory or provisioning scripts that embed shared keys, or leave debug ports or test modes enabled on finished devices. Release pipelines that stop signing images, or keep signing keys in the repository or in plain variables.
Decided from code: partly. Factory processes may be outside the repository.

### [ISO 21434 13] The product can respond to incidents and be updated
Look for: removal of the update path, remote kill or disable function, or the means to revoke a key or certificate. Logging needed to investigate an incident turned off. Updates that can't fix a security issue because the component is frozen or can't be replaced.
Decided from code: partly. Response plans and procedures are kept outside the repository.

### [ISO 21434 14] Decommissioning and end of support don't leave secrets or access behind
Look for: no way to wipe or invalidate keys, personal data, or paired accounts. Credentials that stay valid for a device after it is removed from service. Support end dates or deprecation handling removed.
Decided from code: partly. Procedures are mostly outside the repository.

### [ISO 21434 15] The risk assessment stays in step with changed interfaces and assets
Look for: new interfaces, data flows, assets or trust boundaries added by the change (new bus, new cloud endpoint, new diagnostic service), where the project keeps a threat model or risk assessment in the repository that was not updated. Mitigations named in the threat model removed from the code.
Decided from code: partly. The assessment itself is often kept in other tools.
